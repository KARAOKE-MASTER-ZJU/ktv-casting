# DLNA 1080P 随机定位：实现与验收记录

目标：用户松开进度条至接收端在目标位置恢复画面和声音不超过 500ms。
缓存仅限当前曲目；缓存命中和未命中分别测量。以下局部测试不能替代端到端验收。

## 2026-09-17：普通 MP4 索引和虚拟文件布局

已实现 `src/seekable_mp4.rs`：

- 解析轨道默认值、分片内的样本大小、时长、关键帧标记、显示时间偏移和源文件绝对位置。
- 为普通 MP4 生成完整样本表，将目录放在媒体数据前面。不同源文件中的相同轨道编号重新分配。
- 生成不可变的“输出字节范围 → 源文件字节范围”映射，支持跨文件头、跨音视频样本和文件末尾的精确读取。
- 构建时不读取媒体数据，不运行音视频编解码器。网络获取分片说明和缓存尚待接入。
- 不支持的时间线中断、复杂编辑表等返回错误，不能当作已支持所有 MP4 输入。

发现并修复：源分片 MP4 中的编辑表使用时长 0；转换为普通 MP4 时必须填入时长并保留编码器延迟，否则播放器只输出极少量样本。

离线工具（输出路径必须不存在）：

```sh
cargo run --example flatten_mp4 -- INPUT.mp4 OUTPUT.mp4
```

真实样本：现有 `target/bilibili-1080-mux-test.mp4`，1920×1080 H.264 视频和 AAC 音频，约 285 秒。
本次输出：`target/seekable-mp4-test-v2.mp4`。

| 检查 | 结果 |
| --- | --- |
| 原文件/输出视频包数 | 均为 6,838 |
| 原文件/输出音频包数 | 均为 13,369 |
| 逐包 SHA-256、显示时间、解码时间、时长、大小、关键帧标记 | 所有包完全一致 |
| 读取的初始化与分片说明 | 148,435 字节 |
| 生成的文件头与索引 | 331,979 字节 |
| 本机 debug 构建的索引生成时间 | 单次约 43ms，不含网络 |
| 本地 ffprobe 定位并读取少量包 | 六次约 72–75ms，包含进程启动，不是恢复播放耗时 |

视频关键帧约每 5.005 秒一次。准确定位需要从目标之前的关键帧开始解码并丢弃目标之前的画面；不能将读取到较早关键帧就算作恢复目标位置。

新增 5 个离线测试覆盖字节范围、两源相同轨道编号、开放时长编辑表、负显示时间偏移、关键帧标记、截断输入及不连续时间线。
离线测试共 15 个通过，3 个显式忽略的网络测试，6 个旧有外部环境测试被过滤。
完整旧测试入口不适合无人值守：`test_proxy` 会持续运行 HTTP 服务器，`test_playlist_manager` 访问外部服务并请求切歌且本次失败；设备测试会自动发现并操作设备。
后续 CI 必须先将这些示例式测试和可重复回归测试分开。

## 2026-09-17：曲目缓存与 HTTP 范围服务模块

新增 `src/song_cache.rs` 和 `src/virtual_mp4_http.rs`，尚待绑定实际投屏会话：

- 每首曲目一个独立目录，磁盘按 1MiB 块缓存，容量由调用方明确指定；内存热点最多 4 块，下载并发最多 4。
- 相同数据块的并发请求合并；淘汰时跳过活动读取持有的数据块。
- 上游必须返回与请求完全相符的 206、Content-Range 和字节数，忽略范围的 200 响应不能写入有效缓存。
- 切歌取消信号能中断正在等待的网络请求；缓存及读取引用全部释放后，仅删除该会话自己创建的文件和目录。
- 使用独立暂存文件和原子重命名，避免取消中的后台磁盘写入留下可被读取的半块数据。容量限制针对缓存块，原子落盘期间还会有暂存文件占用。
- HTTP 层支持完整 GET、HEAD、单一闭区间/开放区间/后缀 Range、206、416、ETag、If-Range 和 If-None-Match；不支持的多范围请求按完整 200 响应处理。
- HTTP 输出按需从源块读取，避免把整首合并结果装进内存。

本地测试证据：16 个并发读同一块只下载一次；跨块数据准确；容量为一块时正确淘汰；取消中的读取在测试的 200ms 上限内退出；目录能完整清理；错误上游响应不会被缓存。
HTTP 集成测试验证完整输出和跨文件头/媒体边界的部分响应一致；关闭模拟上游后再次请求，仍能从缓存正确提供数据。
这些都是服务端正确性测试，不是 Kodi 恢复播放的 500ms 验收。

## 2026-09-17：真实远端索引与未缓存读取优化

新增 `src/dash_index.rs`：通过严格的字节范围请求读取文件头、片段索引和每个分片的说明信息，每路最多 4 个并发请求。
任务没有脱离调用方存活的后台下载，取消准备 future 会取消这些请求。
限制片段数量、总说明数据和总样本数量；验证所有样本在自己的媒体数据框范围内。
遇到嵌套索引、一个索引项包含多对分片等尚未支持的结构明确报错，避免静默生成缺失数据的文件。

测试服务器与逐包回归工具：

```sh
cargo run --example serve_dash -- BV1dqj16aECG 18090 131072
python3 scripts/check_mp4_packets.py target/bilibili-1080-mux-test.mp4 http://127.0.0.1:18090/video.mp4
```

已用实际 B 站视频验证：在线输出的 6,838 个视频包及 13,369 个音频包与本地原始样本逐包完全一致。
首次准备完整索引的本机观测约 1.78–3.04 秒，发生在首次加载而非每次定位。

发现的延迟来源：原 HTTP 输出逐个等待视频/音频样本，且首次只需少量数据也必须下载完整 1MiB 块。
改为保持输出顺序的并发读取，默认块大小降至 128KiB，热点内存仍限制为 4MiB。
关键帧跨多个块时并发请求这些块；新增屏障测试：模拟服务器必须同时收到两个块请求才返回，否则测试失败，证明消除了该处串行等待。

同一视频三个独立服务器的诊断结果（毫秒）：

| 目标秒数 | 串行 1MiB | 并行 1MiB | 并行 128KiB |
| --- | ---: | ---: | ---: |
| 185 | 3382.0 | 1546.0 | 654.4 |
| 75 | 2327.8 | 1085.2 | 386.9 |
| 280 | 1403.9 | 687.8 | 223.6 |
| 140 | 1604.4 | 1133.9 | 541.7 |
| 35 | 653.8 | 1039.8 | 376.8 |

限制：每次是新 ffprobe 进程的启动、初始媒体探测、定位并读取 8 个包的合计；各目标第一次访问，但先前请求可能已缓存邻近音频块。
不是严格隔离缓存的分位数基准，也不是接收端画面恢复时间，不能据此宣布 500ms 达标。
第二轮加入跨块并发后，128KiB 五次为 586.9、534.0、278.3、501.2、366.8ms；64KiB 为 629.4、377.7、821.8、479.8、321.6ms。
仍有超过 500ms 的结果；64KiB 没有显示稳定优势，暂保留 128KiB。

启用跨块并发和 128KiB 块后的整首在线逐包校验再次通过；本次读取约 114MB 耗时 51.96 秒，视频时长约 285 秒。
这是当前网络下持续取数快于播放所需速度的证据，但不是手机性能或低尾延迟保证。对比早先 1MiB 配置约 34.57 秒的整首读取，也提示小块有更多请求开销；后续需按定位与连续播放分别调度。
